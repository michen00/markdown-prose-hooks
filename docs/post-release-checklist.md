# Post-release checklist

Everything currently written in a provisional form, and what each thing becomes once the release flow has actually run. Written before the first tag, while the reasons are fresh, because every item here is a small edit that is obvious today and archaeology in three months.

Each item names its file and why it exists. An item is done when the caveat is gone, not when the feature works — a stale caveat is worse than none, because a reader who finds one wrong stops trusting the rest.

The stages are ordered by what unblocks them, and are deliberately keyed to conditions rather than to version numbers. Nothing in stage B can start before stage A, and nothing in stage C should land before stage B is proven.

How many tags that takes is not knowable in advance. `v0.0.1` may not publish cleanly, and the `0.0.x` series exists precisely so that it can fail without costing anything — stage B might begin at `v0.0.2` or at `v0.0.4`. A checklist that named the numbers would be wrong the first time a tag had to be re-cut, and wrong in the direction that matters, since the reader would trust it.

In the event, `v0.0.1` reached both registries. The tag had to be re-cut once before it was pushed, for a reason unrelated to publishing, and the `crates` job needed one re-run; neither cost a version number. So the condition stage B waits on is met — a crate exists for the `-rs` mirror to depend on — and stage B is now gated on the remaining stage A items rather than on a further tag.

## Stage B — the mirrors, proven by the next patch tag

Unblocked by stage A: the `-rs` mirror is a thin wrapper crate depending on the published crate, so it needs a crate on the registry to depend on.

Proven at `v0.0.2`, which published to both registries, produced seven release assets, and regenerated both mirrors on the tag. Closed complete: the last question here, whether to tighten the mirrors' branch ruleset past `deletion`, was answered no on the merits rather than left on hold. Their tag rulesets went the other way in stage C, on a reason that reaches a tag and not a branch — a tag is the thing a consumer pins.

- [x] Create `markdown-prose-hooks-py` and `markdown-prose-hooks-rs`. Created on 2026-08-21 from this repository as a GitHub template, which is why each arrived as a complete copy of it: 434 files, both implementations, the corpus, the notebook, and a live copy of `release.yml` and `smoke.yml` that a tag pushed to either would have fired against a package name it does not own. Both are now reduced to the shape the generator has to produce, seven files each and no workflows, delivering 58K for `-py` and 8K for `-rs` against 1,481K here. Both resolve through `pre-commit try-repo` and their check ids pass. That shaping was done by hand, so it is a target rather than an artifact: the generator replaces it wholesale.
- [x] Configure the mirrors' repository settings, which are not the settings a normal repository wants, because a mirror is force-pushed rather than contributed to. Done on 2026-08-21. Issues, wiki and projects off, since a report filed on a generated view is filed in the wrong place and the readme points upstream. Squash-only merges, no auto-merge, no update-branch, web commit signoff required — all moot with no pull requests, and set so that the settings say so. A description, a homepage pointing upstream, and seven topics each. Actions disabled outright: there are no workflows and there should be none, and a live copy of `release.yml` is exactly what arrived with the template. Dependabot security updates off but its alerts left on, because a pull request into a tree that gets replaced cannot be merged meaningfully while an alert is free information; the fix belongs upstream and reaches the mirror by regeneration.
- [x] Protect the mirrors' default branch without blocking the thing they exist to do. A ruleset named for its own omission, `main-no-delete-force-push-is-by-design`, carrying the `deletion` rule and nothing else. `non_fast_forward` and a `pull_request` rule are both deliberately absent: the first blocks the force-push the generator performs, and the second blocks direct pushes altogether while inviting a human pull request into a tree that is about to be overwritten. Verified after the fact by force-pushing and reverting. The admin bypass means the rule protects against a credential that is not the maintainer's, which is the relevant case, since it is a buggy generator rather than a person that would delete the branch.
- [x] Decide how the generator authenticates to the mirrors, because it determines what else can be protected. Decided on 2026-08-21: a GitHub App. `GITHUB_TOKEN` cannot write to another repository, so a cross-repository push needs a long-lived credential held here — the first this project would hold, and against the posture that deleted `CARGO_REGISTRY_TOKEN` and publishes through OIDC. A deploy key per mirror is the most scoped form, contents-only and tied to one repository with no user identity, but a deploy key cannot appear in `bypass_actors`, so any rule stricter than `deletion` would block it. A GitHub App can be a bypass actor, which is what would make a `pull_request` rule on a mirror expressible: humans forced through review, the generator exempt. The App wins on both counts and the second is the one that decides it. Its private key is long-lived, but what reaches a workflow is an installation token that expires in an hour and is scoped to the repositories the App is installed on — closer to the OIDC posture than a personal access token, which is scoped to a person and therefore to every repository that person can push. And being nameable in `bypass_actors` is what makes a stricter mirror rule expressible at all.
- [x] Create the App and wire it up. Done on 2026-08-21, and exercised: `mirrors.yml` minted an installation token, cloned both mirrors and pushed a tag to each in a real run rather than in principle. Creating one is the single step here that an API cannot do, so it is a maintainer action rather than an agent one. Contents write and nothing else, no webhook, installable on this account only, installed on the two mirrors and not on this repository — the generator reads this tree with the `GITHUB_TOKEN` it already has. Then the app id as a repository variable and the private key as a secret here, set from the file rather than pasted anywhere, and `actions/create-github-app-token` in the generator to mint the short-lived token.
- [x] Decide whether to tighten the mirrors' branch ruleset past `deletion` now that the App exists. A `pull_request` rule with the App as a bypass actor is the shape, and it is not expressible with any other credential, which is the whole reason the choice above mattered. Decided on 2026-08-21: no, and the reason is the argument that kept the rule out of the mirrors' ruleset in the first place. The App made the rule *expressible*, which is not the same as making it *wanted*. What it would prevent is a person pushing to a mirror by hand — which nobody does, and which the next regeneration undoes anyway. What it would add is an invitation to open a pull request against a tree that is about to be replaced wholesale, which is a worse outcome than the one it guards against: a contributor's work would be reviewed, merged, and then overwritten. The verification opportunity that this item was waiting for did arrive — `v0.1.0` regenerates both mirrors with changed content — so this is a decision on the merits rather than a decision deferred for want of a way to check it. `deletion` stays as the only rule on `main`, which is the one thing a buggy generator could do to a branch that no regeneration would undo. Reopen this if a mirror ever becomes somewhere work originates rather than a view of this tree, which is the same condition that would reopen publishing them.
- [x] Write the generator and run it on tag. Three things in the output are decisions rather than transcription and all three survived: the `-py` mirror keeps the upstream distribution name because it is the same package rather than a fork, the `-rs` mirror needs a name of its own because a crate cannot depend on itself, and the `-rs` wrapper carries a copy of `[profile.release]` because a dependency's profile is ignored -- 538,496 bytes without it against 352,656 with. It appends a commit rather than force-pushing a fresh history, which departs from the wording this item used to carry: a consumer pins `rev:`, and replacing the history strands every pin that is not a tag. The tree is still replaced wholesale, and `--force` stays available on a dispatch for the case that needs it. Running it on tag is the next item's business.
- [x] A committed `Cargo.lock` does not make the `-rs` mirror's hook survive a yank, which is worth knowing before anything depends on it. Measured on 2026-08-21 against a real yanked crate. `cargo fetch --locked` honors a lockfile pinning a yanked version and exits 0, where fresh resolution of the same requirement refuses it outright. But `pre-commit` runs `cargo install --bins --root <envdir> --path .` with no `--locked`, and that re-resolves and fails on the yank. So yanking a `markdown-prose-hooks` version breaks the `-rs` hook for every consumer pinned to a mirror rev that names it, not only the crate. The remedy is a property the mirrors already have rather than a new mechanism: regenerate and force-push them at a version that is not yanked, which means the generator has to run on demand and not only on tag. The property that derivation bought — an id or an `entry:` written once, unable to drift between the two — only exists while both copies do. With the mirrors holding the only ids and the two sets disjoint, there was nothing left to keep in step, so authoring each mirror's manifest removed the last duplicate rather than adding one. - [x] Make version tags immutable, on all three repositories. A consumer pins `rev:` and `uses:` to a tag, so a tag that moves silently changes what they run. Done on 2026-08-21, and the rule this item named was the wrong one. `non_fast_forward` blocks a rewind and nothing else, while a mirror tag advances along its own history every time the generator runs, so it would have permitted the one case a pin cares about. `update` is the rule that freezes a ref, and it was probed rather than read: a throwaway tag ruleset here allowed a create, refused a move to a descendant commit, and left a delete through, so all three repositories carry `update` and `deletion` over `refs/tags/v*.*.*`. No bypass actors, not even the admin role the mirrors already carried — a bypass would leave a force push from a maintainer's machine able to move a consumer's pin silently, which is the failure being closed rather than an inconvenience around it. Editing the ruleset is the only way past it, and that is a deliberate and visible act. Probed against the live tags afterwards: `v0.1.0` refused a move, `v0` took one, and both still resolve to the release commit, since `v0` carries no dots and matches nothing.

  Two consequences to accept rather than discover. Re-cutting a version is now refused rather than merely useless, which is the rule both registries already enforced and the tags did not. And the mirrors workflow can no longer repoint a published mirror, so it was rewritten around that instead of against it: it reads whether the tag is already present, refuses to advance a mirror past a tag that cannot follow it, and names the bump as the remedy. Its tag push needs no force any more, because it can only ever create. A generator change now travels with a release the way an implementation change does, with a dispatch as the one exception: a person may move a mirror's `main` past its newest tag, so a readme fix does not cost a version, while what a pinned `rev:` resolves to stays fixed either way.

They took `non_fast_forward` at the same time, which the same change unlocked: the mutation always appends, so the rule that was left out to permit a force push now costs nothing, and the ruleset was renamed because its old name recorded that omission. A `pull_request` rule stays refused, on the stage B grounds that have not changed. Then demonstrated rather than left to construction: a second dispatch, with the rules already in force and the App holding no bypass among them, landed another `verified: true` commit on each mirror and left `v0.1.0` where it was.

## Not blocked on any of this

Worth doing whenever, and listed here so they are not mistaken for release work.

### Testing what the registries serve

Every other job in both workflows builds the thing it tests. `hook` runs `pre-commit try-repo .` against the local path, `action` runs `uses: ./`, `build` runs `uv build` and uploads the result without installing it, and `verify` in the release flow is another checkout. Nothing installed this package from PyPI or from crates.io, so the corpus had never judged a published artifact: a wheel missing a module, or a crate that will not compile from its own package, would have published green. Stage A closed that by hand, for one tag, on one day. `.github/workflows/smoke.yml` closes it for every tag and again every week.

It cannot be turned into a gate, and is not built as one. A version does not exist until it is published, and publication is irreversible, so any test of a registry necessarily runs after the only decision it could have informed. The remedy for a red run is to yank and publish a new version, and a yank hides a version from resolvers rather than removing it. It is built for how fast it reports, not for what it prevents.

"The registry" is three artifacts, and they fail independently, so the tier runs three times rather than once and a red result names the artifact:

| artifact | how the smoke run exercises it |
| -- | -- |
| the PyPI wheel | installed into a fresh virtual environment, then the CLI tier |
| the crates.io crate source | `cargo install --locked --version` at the tag's version, then the CLI tier |
| the release's prebuilt binaries | every checksum against `SHA256SUMS`, then the CLI tier against the one this host can execute |

The third is the one stage B depends on, because `action.yml` starts downloading and executing those binaries. The sdist is not covered: `pip install` prefers the wheel, and forcing the sdist would test a build backend rather than a published artifact.
