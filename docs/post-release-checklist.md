# Post-release checklist

Everything currently written in a provisional form, and what each thing becomes once the release flow has actually run. Written before the first tag, while the reasons are fresh, because every item here is a small edit that is obvious today and archaeology in three months.

Each item names its file and why it exists. An item is done when the caveat is gone, not when the feature works — a stale caveat is worse than none, because a reader who finds one wrong stops trusting the rest.

The stages are ordered by what unblocks them, and are deliberately keyed to conditions rather than to version numbers. Nothing in stage B can start before stage A, and nothing in stage C should land before stage B is proven.

How many tags that takes is not knowable in advance. `v0.0.1` may not publish cleanly, and the `0.0.x` series exists precisely so that it can fail without costing anything — stage B might begin at `v0.0.2` or at `v0.0.4`. A checklist that named the numbers would be wrong the first time a tag had to be re-cut, and wrong in the direction that matters, since the reader would trust it.

In the event, `v0.0.1` reached both registries. The tag had to be re-cut once before it was pushed, for a reason unrelated to publishing, and the `crates` job needed one re-run; neither cost a version number. So the condition stage B waits on is met — a crate exists for the `-rs` mirror to depend on — and stage B is now gated on the remaining stage A items rather than on a further tag.

## Stage B — the mirrors, proven by the next patch tag

Unblocked by stage A: the `-rs` mirror is a thin wrapper crate depending on the published crate, so it needs a crate on the registry to depend on.

- [x] Create `markdown-prose-hooks-py` and `markdown-prose-hooks-rs`. Created on 2026-08-21 from this repository as a GitHub template, which is why each arrived as a complete copy of it: 434 files, both implementations, the corpus, the notebook, and a live copy of `release.yml` and `smoke.yml` that a tag pushed to either would have fired against a package name it does not own. Both are now reduced to the shape the generator has to produce, seven files each and no workflows, delivering 58K for `-py` and 8K for `-rs` against 1,481K here. Both resolve through `pre-commit try-repo` and their check ids pass. That shaping was done by hand, so it is a target rather than an artifact: the generator replaces it wholesale.
- [x] Configure the mirrors' repository settings, which are not the settings a normal repository wants, because a mirror is force-pushed rather than contributed to. Done on 2026-08-21. Issues, wiki and projects off, since a report filed on a generated view is filed in the wrong place and the readme points upstream. Squash-only merges, no auto-merge, no update-branch, web commit signoff required — all moot with no pull requests, and set so that the settings say so. A description, a homepage pointing upstream, and seven topics each. Actions disabled outright: there are no workflows and there should be none, and a live copy of `release.yml` is exactly what arrived with the template. Dependabot security updates off but its alerts left on, because a pull request into a tree that gets replaced cannot be merged meaningfully while an alert is free information; the fix belongs upstream and reaches the mirror by regeneration.
- [x] Protect the mirrors' default branch without blocking the thing they exist to do. A ruleset named for its own omission, `main-no-delete-force-push-is-by-design`, carrying the `deletion` rule and nothing else. `non_fast_forward` and a `pull_request` rule are both deliberately absent: the first blocks the force-push the generator performs, and the second blocks direct pushes altogether while inviting a human pull request into a tree that is about to be overwritten. Verified after the fact by force-pushing and reverting. The admin bypass means the rule protects against a credential that is not the maintainer's, which is the relevant case, since it is a buggy generator rather than a person that would delete the branch.
- [x] Decide how the generator authenticates to the mirrors, because it determines what else can be protected. Decided on 2026-08-21: a GitHub App. `GITHUB_TOKEN` cannot write to another repository, so a cross-repository push needs a long-lived credential held here — the first this project would hold, and against the posture that deleted `CARGO_REGISTRY_TOKEN` and publishes through OIDC. A deploy key per mirror is the most scoped form, contents-only and tied to one repository with no user identity, but a deploy key cannot appear in `bypass_actors`, so any rule stricter than `deletion` would block it. A GitHub App can be a bypass actor, which is what would make a `pull_request` rule on a mirror expressible: humans forced through review, the generator exempt. The App wins on both counts and the second is the one that decides it. Its private key is long-lived, but what reaches a workflow is an installation token that expires in an hour and is scoped to the repositories the App is installed on — closer to the OIDC posture than a personal access token, which is scoped to a person and therefore to every repository that person can push. And being nameable in `bypass_actors` is what makes a stricter mirror rule expressible at all.
- [ ] Create the App and wire it up. Creating one is the single step here that an API cannot do, so it is a maintainer action rather than an agent one. Contents write and nothing else, no webhook, installable on this account only, installed on the two mirrors and not on this repository — the generator reads this tree with the `GITHUB_TOKEN` it already has. Then the app id as a repository variable and the private key as a secret here, set from the file rather than pasted anywhere, and `actions/create-github-app-token` in the generator to mint the short-lived token.
- [ ] Once the App exists, tighten the mirrors past `deletion`. A `pull_request` rule with the App as a bypass actor is the shape: a person is forced through review, the generator is exempt, and the force-push it performs still lands. That rule is not expressible with any other credential, which is the whole reason the choice above mattered.
- [ ] Write the generator and run it on tag. The mirrors are generated and force-pushed, never hand-edited: a hook manifest maintained in two places is a manifest that eventually disagrees with itself. The output shape is now settled and sitting in both repositories to copy from. Three things in it are decisions rather than transcription, and the generator has to reproduce all three: the `-py` mirror keeps the upstream distribution name because it is the same package rather than a fork, the `-rs` mirror needs a name of its own because a crate cannot depend on itself, and the `-rs` wrapper has to carry a copy of `[profile.release]` because a dependency's profile is ignored -- 538,496 bytes without it against 352,656 with.
- [x] A committed `Cargo.lock` does not make the `-rs` mirror's hook survive a yank, which is worth knowing before anything depends on it. Measured on 2026-08-21 against a real yanked crate. `cargo fetch --locked` honors a lockfile pinning a yanked version and exits 0, where fresh resolution of the same requirement refuses it outright. But `pre-commit` runs `cargo install --bins --root <envdir> --path .` with no `--locked`, and that re-resolves and fails on the yank. So yanking a `markdown-prose-hooks` version breaks the `-rs` hook for every consumer pinned to a mirror rev that names it, not only the crate. The remedy is a property the mirrors already have rather than a new mechanism: regenerate and force-push them at a version that is not yanked, which means the generator has to run on demand and not only on tag. It is one more reason the mirrors stay unpublished, since an unpublished mirror can be repointed freely.
- [x] `action.yml` — the `DEVIATION` comment above `runs:` is the specification for this work. Download the prebuilt binary for the tag, add an `implementation` input taking `auto`, `rust` or `python` and defaulting to `auto`, and keep `pip install` as the fallback for a runner with no published binary. **Verify the downloaded binary against `SHA256SUMS` before executing it.** Delete the comment when the work lands. Done on 2026-08-21. The version comes from the action's own `Cargo.toml` rather than from the ref the consumer wrote, so it resolves the same way for a tag, a branch, a commit and a local `uses: ./` — and self-corrects, because a version bumped ahead of its tag finds no manifest and falls back. A missing asset and a wrong checksum are deliberately not the same case: the first says this release covers other platforms, and falls back, while the second stops the run, since a fallback there would turn a failed verification into a silent downgrade. Exercised locally against the real release for all six paths, including a tampered digest, which `sha256sum --check --strict` rejects. `implementation: rust` turns every fallback into an error, and a new `implementation` output names the build that ran.
- [x] `action.yml` — rewrite the `python-version` description. It stops governing the tool and starts governing only the fallback path. Done. It now says the input is read on the fallback path and only there.
- [x] Replace the estimated binary size with the measured one wherever it is still an estimate. The six stopped being estimates at `v0.0.1`, where they ran from 204,288 bytes for the Windows target to 491,992 bytes for the musl one. The largest is therefore 480 KiB, so about a megabyte overstates the download by more than a factor of two, and the smallest and largest are 2.4 times apart, so any single figure describing all six is wrong for five of them. Done everywhere on 2026-08-21: `README.md` and `action.yml` were corrected the day the release made those numbers knowable, and the port spec and the plan followed. `Cargo.toml` names about a megabyte as a budget rather than a measurement, so it stays as written, with the measured range recorded beside it in the plan.
- [x] Say KiB when the number was produced by dividing by 1024. The first correction above wrote 480 KB, which is the binary-unit value under a decimal-unit label: 491,992 bytes is 480 KiB or 492 KB, and neither name fits the other's number. The notebook made the same substitution in three places, so it now prints 344 KiB for the host build, which is still not a seventh number — on Apple Silicon it is the 352,656-byte `aarch64-apple-darwin` asset. Two statements of the repository's own size disagreed for the same reason, one saying 1.4 MB and the other 1.4 MiB: re-measured, the tree is 434 tracked files and 1,516,771 bytes, which is 1.4 MiB and 1.5 MB. Re-measure per release rather than carrying any of these forward.
- [x] `README.md` — remove the `[!NOTE]` about the action provisioning Python. Done, and replaced by a paragraph saying what the action does instead of what it was going to do. The input table gains `implementation`, and `python-version` is described as the fallback's interpreter.
- [x] Decide whether either mirror publishes to a registry of its own, because the answer changes what the generator has to configure and the spec does not settle it. Decided on 2026-08-21: neither. `pre-commit` resolves a hook repository's own package by path in both languages, verified against installed 4.6.0 rather than recalled — `pip install .` for `language: python`, and for `language: rust` a `packages_to_install` of `{('--path', '.')}` reaching `cargo install --bins --root <envdir> --path .` — so a registry entry under either mirror name would serve no channel that `markdown-prose-hooks` does not already serve on both registries. The decisive argument is neither of those. Publishing would put an irreversible act behind a generated force-push, contradicting the one property the mirrors are designed around, and it would repeat the crates.io first-publish sequence this repository has already paid once. `publish = false` in the `-rs` wrapper makes it a guarantee rather than an intention. ### Testing what the registries serve

Every other job in both workflows builds the thing it tests. `hook` runs `pre-commit try-repo .` against the local path, `action` runs `uses: ./`, `build` runs `uv build` and uploads the result without installing it, and `verify` in the release flow is another checkout. Nothing installed this package from PyPI or from crates.io, so the corpus had never judged a published artifact: a wheel missing a module, or a crate that will not compile from its own package, would have published green. Stage A closed that by hand, for one tag, on one day. `.github/workflows/smoke.yml` closes it for every tag and again every week.

It cannot be turned into a gate, and is not built as one. A version does not exist until it is published, and publication is irreversible, so any test of a registry necessarily runs after the only decision it could have informed. The remedy for a red run is to yank and publish a new version, and a yank hides a version from resolvers rather than removing it. It is built for how fast it reports, not for what it prevents.

"The registry" is three artifacts, and they fail independently, so the tier runs three times rather than once and a red result names the artifact:

| artifact | how the smoke run exercises it |
| -- | -- |
| the PyPI wheel | installed into a fresh virtual environment, then the CLI tier |
| the crates.io crate source | `cargo install --locked --version` at the tag's version, then the CLI tier |
| the release's prebuilt binaries | every checksum against `SHA256SUMS`, then the CLI tier against the one this host can execute |

The third is the one stage B depends on, because `action.yml` starts downloading and executing those binaries. The sdist is not covered: `pip install` prefers the wheel, and forcing the sdist would test a build backend rather than a published artifact.

- [x] `tests/test_cli_corpus.py` — let `_runners()` take the Rust binary's path from the environment rather than only from `target/release`. The docstring already promises that a second implementation is one entry in `_runners()` and no change to any test, and this is that entry. Done as `RUST_BINARY`, which resolves the path it is given, because a case runs with its working directory inside a scratch tree and a relative path would otherwise mean one thing to the harness and another to the process it starts. A path that was named and is missing raises rather than skipping: the caller stated which binary it meant. The Python side needed nothing, as expected — `-m` resolves through `sys.executable`, and with a `src` layout a checkout on the working directory does not shadow an installed package. Measured on 2026-08-20 against the wheel from PyPI, with the first entry of the module search path empty and the import landing in `site-packages`.
- [x] `tests/test_cli_corpus.py` — a companion switch that fails when the package under test resolves inside the repository. Without it, a smoke run whose install step quietly did nothing still tests the working tree and still reports green. `REQUIRE_RUST_BINARY` exists for that reason on the Rust side, and this is the same argument on the Python one. Done as `REQUIRE_INSTALLED_PACKAGE`, which asks the interpreter under test where it imports the package from. It tests against `src/` rather than against the whole checkout, because a virtual environment inside the repository is the ordinary layout here: a `site-packages` under the repository root holds a real install, while `src/markdown_prose_hooks` is the working tree whether an editable install or the current directory led there.
- [x] `.github/workflows/release.yml` — a job needing `[binaries, pypi, crates]` that installs the exact version the tag published and runs the CLI tier against all three artifacts. Pin the version rather than resolving the newest, or a release running concurrently makes the job test something else. Bound the retry on the crates.io index: it can lag a publish by seconds, and an unbounded wait converts a propagation delay into a job that never finishes. Done as a `smoke` job calling `smoke.yml`, which takes the tag as an input. Both installs retry six times at twenty seconds, so a lagging index costs at most two minutes and cannot hang the job.
- [x] A scheduled workflow doing the same against the current published version. This is the one that finds later breakage rather than publication mistakes: a yanked transitive dependency, a change in registry behavior, a new Python the wheel does not cover. The release-time job cannot find any of those, because it runs once and passes. Done as a weekly `schedule` on the same file, which resolves the newest release rather than reading a version out of the manifests — those are bumped before a tag is cut, so a manifest read would spend the interval failing to install a version nobody published. One thing to know about it: GitHub disables a schedule after 60 days without repository activity, and reports nothing when it does.
- [x] Decide whether the smoke runs anywhere but Linux. The CLI tier is the tier that pins path handling, line endings and exit codes, which is where Windows diverges, so a Linux-only smoke exercises the platform least likely to break. Decided: all three, matching the `parity` matrix, on the argument in the sentence above. Proven on 2026-08-21 against `v0.0.1` in run 32455079116, where each platform verified all six checksums and ran the tier three times. The interpreter follows the runner image rather than a pin, which is how a Python the wheel does not survive shows up here — Ubuntu resolved 3.12.3, Windows 3.12.10, and macOS 3.14.6, so the wheel is already known to run on an interpreter released after it. Windows skips one case and so reports 35 where the others report 36, which is the permission case `_apply_modes` skips wherever a mode does not take, exactly as it does in `parity`.

The first run of that workflow failed on all three platforms, for a reason none of these items anticipated: it checked out the tag, so it ran the harness that tag carried, and `v0.0.1` predates both switches above. Both were ignored, the guard against an install step doing nothing was inert, and the Rust runner went looking in a build tree it had never built. The harness now comes from the ref the workflow runs on and the corpus still comes from the tag, which is the one split worth remembering here: the switches may postdate a tag, while the specification an artifact was published against may not be replaced by a later one.
